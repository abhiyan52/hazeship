# Seed Data (synthetic fixtures per feature)

Everything this skill produces lives in `Mock/` at the workspace root
(layout in `Mock/README.md`). Read the project's own compliance/data-
handling rules and the project's `_shared/repo-map.md` (copy it from
`_shared/repo-map.template.md` if it doesn't exist yet) first. This skill is
optional and can run at any point after a tech design exists (it reads §4
Data model); it is also usable for ad-hoc seeding outside a feature — then
the "requirements" come from the user directly.

## Hard safety rules

- **Synthetic data only, generated by seeder libraries** (e.g. Faker /
  factory_boy, or the equivalent for your stack). Never copy, sample,
  "anonymize", or paraphrase real records. Every generated record carries an
  unmistakable synthetic marker: emails end `@synth.example`, external/member
  IDs are prefixed `SYN-`, org names prefixed `qa-`.
- **Local databases only — verified, not assumed.** Before running anything,
  read the target repo's active dev settings and check every configured
  database connection: host must be `localhost`/`127.0.0.1`/empty (sqlite).
  Any other host → STOP and show the user what was found. Never run against
  shared/staging/production databases even if asked casually — that needs
  the user restating the host explicitly after seeing the warning.
- **Tenant isolation**: each feature gets its own organization/tenant named
  `qa-<feature-slug>`. All seeded rows belong to it (directly or via FK
  chain). Wiping a feature's data = deleting that tenant subtree — seed
  scripts must include a `--wipe` mode that does exactly that and nothing
  else.

## Steps

1. **Read the requirements**: the feature's `02-tech-design.md` §4 (data
   model & APIs) and §5 (sensitive-data flow — tells you which fields need
   obviously-synthetic values), plus the dev plan's test strategy if slices
   need specific scenarios (edge cases, volumes). No tech design → ask the
   user for the models/tables and scenario shapes needed.
2. **Consult schema notes**: `Mock/schemas/<repo>.md`. If present, trust but
   verify (models drift); if absent or stale, introspect the repo's actual
   models (its ORM shell, or reading the model definitions directly) for the
   apps involved.
3. **Write the seeder** under `Mock/<feature-slug>/`:
   - `factories_<repo>.py` — factory_boy factories with Faker providers (or
     the equivalent for your stack), synthetic markers baked in, and the
     feature tenant as the default org.
   - `seed_<repo>.py` — runnable script: creates/gets the `qa-<slug>`
     tenant, seeds in dependency order, supports `--wipe`, `--validate`
     (checks only, no writes), and `--count` overrides. Idempotent:
     deterministic `get_or_create` keys, so re-runs don't duplicate.
   - `notes.md` — what/why, tenant name, exact run/wipe commands, scenario
     inventory (which dev-plan scenarios this data supports).
   - Scripts run against the repo via its own environment (e.g.
     `<DEV_SETTINGS_ENV_VAR>=<dev settings> python Mock/<slug>/seed_<repo>.py`)
     — never copy scripts into the product repos, never modify repo code.
     If the seeding libraries are missing from the repo's environment, tell
     the user the exact install command; don't edit the repo's dependency
     manifests.
4. **Run** (with the user's go-ahead) and **validate — this skill owns data
   quality**; a broken seed is worse than no seed. `--validate` must check,
   and the post-seed run must report:
   - Row counts per model vs. requested.
   - FK integrity and tenant closure: every seeded row reachable from the
     `qa-<slug>` tenant; zero rows attached to other tenants.
   - Model-level validity: full validation on a sample per model; app-level
     invariants from the tech design (e.g. status enums, date ordering).
   - Synthetic-marker audit: no seeded text field looks like a real
     identifier (all emails `@synth.example`, IDs `SYN-`-prefixed).
   Any failure → wipe the partial seed, report verbatim, fix the script,
   re-run. Never leave a half-seeded tenant behind.
5. **Update the durable schema notes**: rewrite `Mock/schemas/<repo>.md`
   from what you actually introspected and seeded — per app: models, key
   fields/types, FK graph (mermaid ok), tenancy anchor field, constraints
   that bit you, `last-verified: <date>`. This file is why the next seeding
   run starts fast.
6. **Report**: tenant name, counts per model, run/wipe/validate commands,
   validation results, and a line in the feature's slice log (or notes.md if
   outside a feature) recording that seeded data underpins the test
   evidence. If the feature has a manifest, append a handoff entry
   (stage: seed-data helper — informational; this skill never touches
   stage/gate/slice state).

## Storage contract (`Mock/`)

Tracked in the meta repo: scripts, factories, notes, schema md files —
they're code, review them like code. Gitignored: `Mock/**/output/` (dumps,
generated CSV/JSON exports). Nothing in `Mock/` may ever contain real
user/production data — that rule makes the whole tree safely committable.
