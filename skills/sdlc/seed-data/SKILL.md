# Seed Data (synthetic fixtures per feature)

Everything this skill produces lives in `seeds/` at the workspace root
(layout at the end of this file). Read the data handling rules and the rest
of the project's `_shared/repo-map.md` (copy it from
`_shared/repo-map.template.md` if it doesn't exist yet) first. This skill is
optional and can run at any point after a tech design exists (it reads §4
Data model & APIs and §5 Data handling); it is also usable for ad-hoc seeding
outside a feature — then the "requirements" come from the user directly.

## Adapt to the project's stack — don't assume one

Nothing here is tied to a language, ORM or framework. Before writing
anything, establish from `_shared/repo-map.md` (or from the repo itself if
the map is silent — then tell the user to record the answer there):

- **Seeder library**: what the repo already uses, or the idiomatic choice for
  its stack — a factory library plus a fake-data generator, the framework's
  own seeding/fixture mechanism, or plain scripts against a migration-aware
  client. Prefer what's already there over introducing a dependency.
- **How a script runs against the repo**: the exact command, including the
  env var or config flag that selects dev settings.
- **How to introspect the schema**: model definitions, migration files, or a
  database introspection command.
- **Isolation strategy** (see the hard rules below).
- **Naming**: match the repo's conventions. The filenames in this skill are
  shapes, not literal names.

If the repo has no seeding mechanism at all, say so and propose one — don't
silently stand up a parallel system beside it.

## Hard safety rules

Stack-independent and non-negotiable.

- **Synthetic data only, generated by a seeder/faker library.** Never copy,
  sample, "anonymize", or paraphrase real records. Every generated record
  carries an unmistakable synthetic marker. Defaults, unless the project
  records its own in `_shared/repo-map.md`:
  - emails end `@synth.example` (`.example` is reserved and cannot resolve)
  - external/reference identifiers are prefixed `SYN-`
  - human-readable names are prefixed `qa-`
- **Local databases only — verified, not assumed.** Before running anything,
  read the target repo's active dev configuration and check every configured
  database connection: the host must be `localhost`, `127.0.0.1`, or empty
  (a local file-backed database). Any other host → STOP and show the user
  what was found. Never run against shared/staging/production databases even
  if asked casually — that needs the user restating the host explicitly
  after seeing the warning.
- **One deletable root.** Every seeded row must be reachable from a single
  key that can be deleted to remove the whole batch, so a seed is always
  reversible. What that key is depends on the schema — take it from
  `_shared/repo-map.md`, in this order of preference:
  1. a natural scoping entity, if the schema has one (tenant, organization,
     workspace, account, project)
  2. a dedicated seed user/owner that owns the whole graph
  3. a batch column or tag, e.g. `seed_batch = "qa-<feature-slug>"`
  4. last resort: a recorded manifest of the primary keys the script wrote

  Where the key is a value you choose, name it `qa-<feature-slug>`. Wiping
  the feature's data means deleting that root's subtree and nothing else.

## Steps

1. **Read the requirements**: the feature's `02-tech-design.md` §4 (data
   model & APIs) and §5 (data handling — tells you which fields need
   obviously-synthetic values), plus the dev plan's test strategy if slices
   need specific scenarios (edge cases, volumes). No tech design → ask the
   user for the entities and scenario shapes needed.
2. **Consult schema notes**: `seeds/schemas/<repo>.md`. If present, trust but
   verify (schemas drift); if absent or stale, introspect the repo's actual
   schema by whichever means it supports.
3. **Write the seeder** under `seeds/<feature-slug>/`, in the project's own
   language and conventions:
   - **Factories/fixtures** — one definition per entity, synthetic markers
     baked in, and the isolation key applied by default so no call site can
     forget it.
   - **A runnable seed script** — creates-or-gets the isolation root, seeds
     in dependency order, and supports:
     - `--wipe` — delete the isolation root's subtree, and nothing else
     - `--validate` — checks only, no writes
     - `--count` — override per-entity volumes

     Idempotent: deterministic get-or-create keys, so re-runs don't
     duplicate.
   - `notes.md` — what/why, the isolation key's value, the exact run/wipe/
     validate commands, and a scenario inventory (which dev-plan scenarios
     this data supports).
   - Scripts run against the repo through its own environment and config —
     never copy scripts into the product repos, never modify repo code. If
     the seeder libraries are missing from the repo's environment, tell the
     user the exact install command; don't edit the repo's dependency
     manifests yourself.
4. **Run** (with the user's go-ahead) and **validate — this skill owns data
   quality**; a broken seed is worse than no seed. `--validate` must check,
   and the post-seed run must report:
   - Row counts per entity vs. requested.
   - Referential integrity and isolation closure: every seeded row reachable
     from the isolation root; zero rows attached to anything else.
   - Entity-level validity: the project's own validation layer run over a
     sample per entity, plus the app-level invariants from the tech design
     (status enums, date ordering, and so on).
   - Synthetic-marker audit: no seeded text field looks like a real
     identifier (markers per the rules above).

   Any failure → wipe the partial seed, report verbatim, fix the script,
   re-run. Never leave a half-seeded root behind.
5. **Update the durable schema notes**: rewrite `seeds/schemas/<repo>.md`
   from what you actually introspected and seeded — per module: entities, key
   fields and types, the reference graph (mermaid is fine), the isolation
   anchor field, constraints that bit you, and `last-verified: <date>`. This
   file is why the next seeding run starts fast.
6. **Report**: the isolation key, counts per entity, run/wipe/validate
   commands, validation results, and a line in the feature's slice log (or
   `notes.md` if outside a feature) recording that seeded data underpins the
   test evidence. If the feature has a manifest, append a handoff entry
   (stage: seed-data helper — informational; this skill never touches
   stage/gate/slice state).

## Storage contract (`seeds/`)

```
seeds/
├── <feature-slug>/       # factories, seed script, notes.md
└── schemas/<repo>.md     # durable schema notes, one per repo
```

Tracked in the meta repo: scripts, factories, notes and schema files — they
are code, so review them like code. Gitignored: `seeds/**/output/` (dumps and
generated exports). Nothing under `seeds/` may ever contain real user or
production data — that rule is what makes the whole tree safely committable.
